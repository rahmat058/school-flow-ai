- 2026-09-24 — **§4.14 (Reports) synced to the new frontend reports module.** The frontend now ships `/reports` with four tabs, so the checklist was rewritten from the two `?from=&to=` aggregates into the four reads the screens actually call: `GET /reports/overview` (active counts, collected/pending, the twelve-month series, the class catalogue), `GET /reports/attendance?month=&year=&classId=` (present/total/percentage per class for the month), `GET /reports/exam-results/papers` plus `GET /reports/exam-results?paperId=` (one paper's marks per student with `totalStudents`/`passed`/`failed`/`averagePercentage` and the grade distribution; 404 `REPORT_PAPER_NOT_FOUND`), and `GET /reports/finance` (totals, collection rate, the series, and every invoice still carrying a balance, soonest-due first). `/reports/students/:id` and `/reports/export` stay as they were and `/dashboard/admin` is untouched. **Behaviour** records what the implementation must keep: the module owns **no tables** — every figure aggregates from attendance/fees/exams/classes/people; attendance counts **present and late** and **omits** a class with no register day rather than reporting a zero (an empty month is empty, not an error); the exam report is **per paper**, because the screen reads one subject at a time, and a student holding no mark stays in `totalStudents` but out of `passed`/`failed`/`averagePercentage`; finance rows are billed **net of concession** so `total − paid = balance` holds, and the collection rate is `collected ÷ (collected + pending)`; and the monthly series is the **same** one `GET /fees/dashboard` returns, so the two screens cannot disagree. **`Database.md` §16** now names the projection behind each endpoint (`mv_attendance_monthly`, `mv_fee_collection`, plus the on-demand RPCs) and says plainly that the module adds no table. No schema change is implied, so no migration is needed.

- 2026-09-24 — **§4.4 (Classes & subjects) rewritten around a subject catalogue, and a new `class_subjects` table.** The frontend now ships a Subject & Class module (a catalogue tab with add/edit/delete, an assignment tab, and a summary matrix), which needed a model the schema did not have: `subjects` was **one row per (class, subject)** with a class-suffixed code (`MATH-5A`), so a subject had no school-wide identity and the teacher sat on the subject. **`subjects` is now the catalogue** — `id`, `school_id`, `name`, `code`, `description`, `unique (school_id, code)` — with **`class_id` and `teacher_id` dropped**, and a new **`class_subjects`** join (`school_id`, `class_id`, `subject_id`, `teacher_id`, `unique (class_id, subject_id)`) carries the assignment _and_ the teacher. That is the modelling decision worth keeping: the **teacher belongs to the assignment**, because the same subject is taught by different staff in each class, and it is what lets a code read `MATH` school-wide instead of `MATH-5A`. **Endpoints (§4.4):** `POST /subjects` (catalogue create, 400 on a malformed code, 409 `SUBJECT_CODE_TAKEN`/`SUBJECT_NAME_TAKEN`), `GET /subjects` (catalogue, `?classId=`/`?teacherId=` scoped), `GET /subjects/overview` (catalogue + `classCount`/`classIds`), `PATCH /subjects/:id` (also takes an optional `classId` — see the later entry), `DELETE /subjects/:id` (cascades its assignments; **409 `SUBJECT_IN_USE`** while a lesson, paper, mark, homework or material references it), `GET /subjects/assignments?classId=`, `POST /subjects/assignments` (idempotent add), `POST /subjects/assignments/bulk`, `DELETE /subjects/assignments/:classId/:subjectId` and `GET /subjects/summary`. **Behaviour** records the two rules the implementation must keep: a subject is only meaningful **with** a class — every module taking a `subjectId` alongside a `classId` validates the pair against `class_subjects` and 400s otherwise (homework, materials, timetable slots, tests, exam papers) — and an assignment write is **additive** (the grid offers what the class does not run yet; bulk inserts only the missing pairs). **`Database.md` moved in the same pass:** §4's intro ERD, the `classes` per-table ERD, the rewritten `subjects` spec, the new `class_subjects` spec with its own ERD, §13's FK map (the three `subjects` FKs become one plus four on `class_subjects`), §14's index plan, §15's inventory (36 → **37 tables**, renumbered), §17's coverage row and §19's full ERD (37 tables, **95 FKs**, `schools` fanning out to 33). No `subject` enum exists — name and code are the school's own data, so nothing was added to §2.

- 2026-09-24 — **`POST /subjects` accepts an optional `classId`, so the Add Subject form can create and assign in one call.** The frontend's Add Subject sheet gained an "Assign to class" picker (every class, plus _Leave unassigned_), so the endpoint takes an optional `classId`, creates the catalogue row and inserts the matching `class_subjects` row in the same request — 400 `SUBJECT_INVALID` when the class does not exist. `PATCH /subjects/:id` initially **did not** take one — that was reversed by the next entry, which lets the edit form move a subject. No schema change — the response's `classCount` simply reflects the new join row. Behaviour in §4.4 records it alongside the additive-assignment rule.

- 2026-09-24 — **`PATCH /subjects/:id` now takes `classId`, and §4.4's docs were reconciled with the data flow.** Editing a subject can **move it**: a `classId` key replaces that subject's `class_subjects` rows with the one chosen (empty clears them), an **absent** key leaves them alone — which is what the form sends when a subject already sits in several classes, so the single picker cannot silently drop the rest. The replace keeps the chosen link rather than deleting and re-inserting it, so an unchanged choice keeps its teacher instead of regenerating one from the rotation. The audit of the class/subject model against the mock turned up four mismatches, all now fixed in both directions: **`subjects.name` is unique per school** in the mock (409 `SUBJECT_NAME_TAKEN`) but the schema listed only the code — §4's Keys/Indexes and §14's index plan now carry `unique (school_id, lower(name))` and say both are compared **case-insensitively** (`Math` cannot shadow `MATH`; `lower(...)` indexes or `citext`); **`SUBJECT_IN_USE` did not check `results`**, though §13 marks `results.subject_id` `restrict` — the guard now mirrors the full restrict set (`homework`, `study_materials`, `exam_subjects`, `results`, `periods`) and §4/PRD list marks among the five referencing tables; **`GET /subjects/overview`** returns `classIds` beside `classCount` (the read-only list the edit form shows) and the PRD says so; and **`class_subjects`** gained a note on who writes a row, because the earlier PRD line claimed the opposite. **The `classId` parameter itself was then dropped — see the next entry.** No migration is implied beyond the `lower(...)` unique indexes, which belong in the initial `subjects` DDL.

- 2026-09-24 — **The `classId` parameter was removed from `POST`/`PATCH /subjects` — assignment has one writer.** `PATCH /subjects/:id` taking a class was reversed the same day: assignment now has exactly one home, the assignment endpoints, so both catalogue writes take `name`, `code` and `description` only and leave `class_subjects` untouched (a new subject is taught in **no** class). §4.4's Behaviour bullet says so, `GET /subjects/overview`'s `classIds` is documented as the **read-only** list the edit form shows rather than a picker pre-fill, and `class_subjects`' note went from "two ways a row is written" to **one writer** — the additive assignment endpoints plus the per-pair delete. The `SUBJECT_IN_USE` set (now including `results`) and the `lower(...)` unique indexes from the previous entry stand; the only change here is who may write an assignment. No schema change.

- 2026-09-25 — **§4.1 (Schools) synced to the new Settings module, and `schools.settings` was given a shape.** The frontend now ships `/settings` — a four-tab screen (School Profile / Academic / Notifications / Security) behind the ADMIN guard, replacing the old `PlaceholderPage` — so the contract was rewritten to match what the tabs call, and `schools.settings` went from the phrase "academic year, grading scheme, fee heads, branding" to a **specified document**. **Endpoints:** the `GET`/`PATCH /schools/:id/settings` pair is **superseded** — the screen edits the caller's own school, so a school id never appears in the path. `GET /schools/current` now returns the profile **and** the whole `settings` document; `PATCH /schools/current` writes the profile columns (a blank contact field clears to `null`; the slug is **not** regenerated, so stored links survive a rename); `PATCH /schools/current/settings` **merges** a partial patch so the four tabs cannot overwrite one another; and `POST /schools/current/backup` answers `201` with a job record. **Schema:** no new column and **no migration** — `settings` is one JSONB document, now specified key by key in `Database.md` §3 (academic keys at the root beside `currency`/`timezone`/`gradingScheme`, plus nested `notifications` and `security` objects) with its defaults. The unions (`gradingScale` ∈ `PERCENTAGE|LETTER|GPA`, `termStructure` ∈ `SEMESTER|TRIMESTER|ANNUAL`), the ranges (`passPercentage` 0–100, `sessionTimeoutMinutes` 5–240, `maxLoginAttempts` 1–10) and the `SETTINGS_INVALID` 400 are contract-level, enforced in the DTO rather than by Postgres — recorded as `Database.md` §18 q16, because an untyped document is only caught at write time. **Docs moved with it:** `Design.md` gained the `current`-addressing rule, `Rules.md` the "validate the JSONB in the DTO, merge on `PATCH`" rule, `Architecture.md`'s `schools/` line, and `Phases.md`'s Phase 1 settings line. **Frontend contracts that drove it:** each tab owns a form and posts only its slice, one header _Save Changes_ button submits whichever tab is open, the demo seeds `passPercentage: 40` to agree with `lib/grades.ts` (the reference screenshot's `35` was not adopted, and neither was its orange accent — indigo stays the only interactive colour), and the panel's style follows `Design.md` rather than the screenshot: hero primary `#6366F1`, a neutral section icon chip, and toggles flipped to the right of their labels.

- 2026-09-25 — **§4.14 gained `GET /dashboard/student`, because the dashboard now branches by role.** The frontend lands a student on their **own** day instead of the school-wide admin view, so the contract needed a second dashboard endpoint: the caller's attendance rate with its present/absent/late split and the last few register days, `paid`/`pending`/`total` fees with the invoice list and the paid share, today's teaching periods for their class, the papers still ahead, and the notices they are in the audience of. **It is self-scoped** — the student comes from the session, so no id appears in the path and a non-student account is refused with `403 DASHBOARD_FORBIDDEN` (the mock returns it for both an admin and a teacher token, and `401` without a token). Three rules the implementation must keep, recorded in §4.14's Behavior block: every figure **reuses the read model the student's own screens already show** (the register totals behind the profile's Attendance tab, the invoices behind Fee history, the class grid behind `/timetables/me`), so the dashboard and those screens cannot disagree; fees are billed **net of concession**, so `paid + pending = total` and `progress = paid ÷ total`, with `today` **`null`** on a non-school day and **breaks excluded** from the periods; and notices are the **published** ones whose audience is `ALL`/`STUDENTS` **and** whose class targeting is empty or includes the student's class. **No schema change** — `Database.md` §16 adds the endpoint to the on-demand RPC list beside `/dashboard/admin`, and `Phases.md` Phase 4's reports line now reads "admin + student dashboard endpoints". **Frontend contracts that drove it:** a student's home is role-selected in `DashboardPage`, and the reference screenshots' currency and orange accent are not adopted (the demo student reads USD via `formatPaise`).

## Decisions

- Stack locked: NestJS + Supabase (PostgreSQL) (replacing original MERN/Prisma plan)
- Payments: Stripe (international) + SSLCommerz (Bangladesh) — Razorpay removed
- Email: Resend (transactional API) — Nodemailer/SMTP removed
- Email templates: React Email (`react-email`) `.tsx` components rendered to HTML with `render()`, sent via Resend — Handlebars/raw-HTML string templating dropped
- Money stored as integer paise; dates ISO-8601; UUIDs for all IDs
- Multi-tenant via `schoolId` on every table + tenant guard — do not add unscoped queries
- API contract defined in `docs/backend/Design.md` — follow envelopes exactly
- Recharts on frontend (not Chart.js) — chart endpoints should return plain series data
- DB identifiers are `snake_case` (Postgres/Supabase idiom, no quoted identifiers in raw SQL); services map them to the camelCase JSON required by `Design.md`. The PascalCase/camelCase names in PRD §3 are logical model names, not table names — see `docs/backend/Database.md` §1.
- ERD reference: `docs/backend/Database.md` is the schema source of truth alongside `supabase/migrations/` — change both together.
- `homework.max_marks` is a **nullable integer ceiling** for a graded submission (`null` = the task is unmarked), added when the frontend's assignment form landed. Grading itself still records a free-text `grade` + `remarks` on `homework_submissions` — `max_marks` only bounds what that grade is out of.
- Timetable period rows are **stored per day** (`periods` under each day's `timetables` row) but **managed class-wide** — a row is added to or removed from every day in one transaction and addressed by its `orderIndex`. That keeps the days from drifting apart without adding a class-level period table to the schema. `periods.label` names a row; a null label on a teaching row derives `Period n` over teaching rows only.
- `notices.priority` is a new `notice_priority` enum (`HIGH`/`MEDIUM`/`LOW`, default `MEDIUM`) that tints the board card; it deliberately does not reorder the feed. `notices.author_name` stores the byline the board form collects (blank falls back to the publisher's display name) — the frontend seed already carried `authorName` as a read-model field with no column behind it. Notices have no draft state in the UI: create publishes, and editing a draft publishes it.
- **Subjects are a school-wide catalogue with a per-class assignment.** `subjects` holds one row per subject the school teaches (`name`, `code`, `description`, `unique (school_id, code)`) — **not** one row per class as it originally did — and **`class_subjects`** (`class_id`, `subject_id`, `teacher_id`, `unique (class_id, subject_id)`) is the assignment. The **teacher sits on `class_subjects`**: the same subject is taught by different staff in each class, so a subject-scoped teacher would be wrong the moment a second class takes it. Every module that stores a `subject_id` alongside a `class_id` (homework, study materials, periods, exam papers, results) must therefore treat the pair as the key and validate it against `class_subjects`. `code` is the school's own and is **no longer suffixed with the class** — the previous `MATH-5A` form existed only because the row was class-scoped; a code is now unique per school and reads `MATH` everywhere. Deleting a subject cascades its `class_subjects` rows but is refused (409 `SUBJECT_IN_USE`) while `homework`, `study_materials`, `exam_subjects`, `results` or `periods` still reference it — the `restrict` side of those FKs. There is deliberately **no `subject` enum**: name and code are admin data, edited in the Subjects tab, so an enum would have to be migrated every time a school adds a subject.
- **School settings are one JSONB document on `schools`, grouped by the Settings screen's tabs** — the academic keys (`academicYear`, `gradingScale`, `termStructure`, `passPercentage`) sit at the root beside `currency`/`timezone`/`gradingScheme`, with nested `notifications` and `security` objects. Each tab `PATCH`es only its own slice and the write **merges**, so no tab can drop another's keys. `gradingScale` and `termStructure` are contract unions rather than DB enums because they live in JSONB; the demo's `passPercentage` is 40 to match `lib/grades.ts`. The Settings screen never carries a school id — `current` addresses the caller's own school, since the tenant comes from the session, so `GET`/`PATCH /schools/:id/settings` no longer exists.
